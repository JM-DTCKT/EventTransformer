# fpga_dvs128_10 — EvT(DVS128 제스처) 가속기, attention 포함

`fpga_nl` 이 비선형 유닛과 16비트 포맷을 보드에서 검증했으니, 여기는 **attention 과
마스킹이 들어간 실제 EvT** 를 올립니다.

호스트 쪽(전처리·골든·tap)은 [`EventTransformer/real_dvs_script/`](../../01_assignment/EventTransformer/real_dvs_script/)
에 있고, 양자화는 [`EventTransformer/quantization/`](../../01_assignment/EventTransformer/quantization/)
결과를 **재배치만** 합니다.

---

### ping-pong 은 **정확도를 한 톨도 안 건드렸습니다**

같은 264 샘플을 ping-pong 전/후로 돌린 결과가 **구간별 오답 분포까지 같습니다**:

```
구간        ping-pong 전   ping-pong 후
 20- 39         2              2
 80- 99         1              1
140-159         1              1
160-179         1              1
240-259         1              1
나머지          0              0
합계            6              6
```

설계대로입니다 — `PE_OS_Pp` 는 **언제 읽느냐**만 바꿉니다 (DSP48E2 매핑·연산 무변경,
§1.6). `tb_evt` 140,170 검사가 전부 같았던 것이 보드에서 그대로 재현됐습니다.

| | ping-pong 전 | **ping-pong 후** | |
|---|---|---|---|
| 정확도 | 258/264 = 97.72 % | **258/264 = 97.72 %** | 동일 |
| 샘플당 (벽시계) | 24,637 us | **16,765 us** | **1.470배** |
| 264 샘플 | 6,504 ms | **4,426 ms** | **1.470배** |
| 엔진 사이클 (last run, 같은 샘플) | 2,441,437 | **1,662,996** | **−31.9 %** |

§1.6 시뮬 예측(1,623,399)과 **+2.44 %** — 예전 빌드의 같은 비교(+2.03 %)와 같은
크기입니다. 이 차이는 타임스텝마다 토큰을 DMA 로 올리는 호스트 오버헤드이고
시뮬에는 없는 부분입니다. 8샘플 브링업(16,897 us)과도 **−0.78 %** 로 맞습니다.

### 골든과의 대조 — **틀리는 자리가 같습니다**

개수만 보면 안 됩니다. 20개 구간별 오답 분포가 골든이 틀리는 샘플
(27·39·97·141·152·171·243)과 거의 그대로입니다:

```
구간        실패   골든
 20- 39      2      2
 80- 99      1      1
140-159      1      2     <-- 여기 하나만 다름
160-179      1      1
240-259      1      1
나머지       0      0
합계         6      7
```

**다른 곳 없이 140~159 에서 하나(141 또는 152)만 맞는 쪽으로 넘어갔습니다.**
새 softmax/LayerNorm 코어는 반올림 자리가 골든(전수 LUT)과 달라 확률 1 LSB 가
갈리는데(§1.5), 경계에 있던 샘플 하나가 그 1 LSB 로 뒤집힌 것입니다.

> **이걸 정확도 개선으로 읽으면 안 됩니다.** 264개 중 1개는 통계적 잡음이고,
> 방향이 반대였을 수도 있습니다. 의미 있는 신호는 **나머지 6개가 골든과 정확히
> 같은 자리**라는 것 — 즉 재현이지 우연이 아니라는 쪽입니다.
> 예전 코어 빌드는 7개가 골든과 **완전히** 일치했습니다 (아래 표).

## 1.5 비선형 코어 교체 — 지연 4.6배 단축

`SOFTMAX/` `LAYERNORM/` 의 새 코어로 갈아끼웠습니다. 예전 것은
`Softmax_origin/` `LayerNorm_origin/` 에 남아 있고 `fpga_nl` 이 그걸 씁니다.

| | 예전 | 새 코어 |
|---|---|---|
| softmax (Lk=53) | 6,800 사이클 | **151** |
| LayerNorm (타일 3개) | 5,376 사이클 | **572** |
| 타임스텝 하나 | 571,363 | **124,628** → §1.6 뒤 **87,717** |
| **샘플 하나 (20 타임스텝)** | **10,558,819 = 105.6 ms** | **2,392,882 = 23.9 ms** → §1.6 뒤 **1,623,399 = 16.2 ms** |
| **샘플 하나 (보드 실측)** | **108.4 ms** | **24.6 ms  (4.40배)** → §1.6 뒤 **16.8 ms (6.46배)** |
| **264 샘플 (보드 실측)** | **28.61 초** | **6.50 초** → §1.6 뒤 **4.43 초** |
| 정확도 (264 샘플 실측) | 257/264 | **258/264** |

보드 실측 2,441,437 사이클은 시뮬레이션(2,392,882)보다 **2.0 %** 큽니다 —
타임스텝마다 토큰을 DMA 로 올리는 호스트 오버헤드이고 시뮬에는 없는 부분입니다.

softmax 가 타임스텝의 절반 가까이를 쓰고 있었습니다 — 예전 판은 레인 하나를
시분할해 `4·N·C` 였고 그걸 (행타일 3)×(head 4)×(블록 3) = 36번 돌았습니다.
새 코어는 열(32행)을 매 사이클 받아 max 를 수신 중에 확정하고 RECV/EXP/MUL 을
**서로 다른 Tile 로 겹칩니다.**

### 래퍼로 감쌌습니다 — 엔진은 바뀐 줄 모릅니다

`rtl/Softmax_Attn.v` 와 `rtl/LayerNorm_Ev.v` 가 엔진 쪽 인터페이스를 그대로
유지하면서 안쪽만 새 코어로 바꿉니다. 맞춰 준 것:

| | |
|---|---|
| softmax | `C` → `in_last`, 출력 Q1.14 → **uint8**(`softmax_scale` 의 역수) |
| LayerNorm | A_Mem 읽기 스트리밍, **affine(gamma/beta)**, Q4.11 → int8 재양자화 |

새 LayerNorm 코어는 정규화만 합니다. 코어 주석은 "gamma/beta 를 다음 Linear 에
접어라" 지만, 그러면 **가중치 양자화 격자가 바뀌어 골든과 어긋납니다.** 그래서
예전과 똑같이 `LN_Affine` 을 래퍼에서 씁니다.

행타일 반복도 엔진에서 **래퍼로 옮겼습니다.** 코어의 3단 Tile 파이프라인이
겹치려면 타일을 끊지 않고 연달아 밀어야 하기 때문입니다.

### `in_shift` 는 캘리브레이션 격자로 정하면 안 됩니다

새 LayerNorm 코어는 내부가 Q8.15(±256) 이고 입력을 `value·2^xsh` 로 옮겨 넣습니다.
골든의 `layer_norm_1.in` 은 **Q16.-1(범위 65536)** 인데 실측 입력은 **0.74** 입니다
— 20 타임스텝 누적 최악치로 잡힌 격자라 실제보다 수천 배 넓습니다. 그대로
`xsh = f-8 = -9` 를 주면 정밀도가 5비트로 줄어 결과가 무너집니다(실제로 그랬습니다).

골든 덤프에서 잰 실측치로 잡습니다 — 블록 안 LN 은 `xsh=2`, 20 타임스텝을 받는
`proc_embs_block.layer_norm` 만 `xsh=-2`. LayerNorm 은 스케일 불변이라 이 값은
**정확도가 아니라 정밀도**만 바꿉니다.

### 골든과 비트 일치는 원리상 안 됩니다

두 코어 모두 **산술이 다릅니다** — LayerNorm 은 정수 분산 + rsqrt LUT(예전은
bf16 누산), softmax 는 exp2 기반 Q1.14(예전은 exp/recip LUT + uint8 직행).
실측 편차와 그에 맞춘 판정 기준:

| | |
|---|---|
| `layer_norm_x` | 6,474/6,656 정확, 나머지 ±2 |
| 잔차 뒤 int8 (`LNA1` `FFN3` `TFFN` …) | ±4 |
| 분류기 누산기 10개 | **3 % 이내** → 클래스 순위 안 바뀜 |
| `res_class` | **9 = 정답** |

`tb_softmax_attn` 은 **예전 코어의 LUT 산술을 비트 단위로** 보던 TB 라 더는 안
맞습니다. 대신 `tb_smx_wrap`(길이 53↔97 교대 + 출력 합 ≈127)과 `tb_ln_wrap`
(타일 3개 열 수)을 새로 두었습니다.

### 합성에서 잡은 것 — **3차원 배열은 BRAM 이 안 됩니다**

첫 빌드가 **배선 실패**했습니다 (`global congestion level 6`). 원인은 softmax 의
버퍼가 BRAM 이 아니라 **플립플롭 27만 개**로 깔린 것이었습니다.

```
WARNING: [Synth 8-11357] Potential Runtime issue for 3D-RAM ...
   xbuf_reg with 132096 registers    ebuf_reg with 140352 registers
레지스터 63,469 → 364,039 (66 %)
```

`xbuf [0:1][0:TMAX-1]` 처럼 **뱅크를 차원으로** 두면 Vivado 가 3D-RAM 으로 보고
BRAM 추론을 포기합니다. 같은 파일의 `layernorm_top` 은 `xbuf [0:NB*D-1]` 로
평탄화돼 있어 정상적으로 BRAM 이 됐습니다 — 그 차이가 전부였습니다.

주소를 `{뱅크, 열}` 로 이어 평탄화했습니다. 깊이는 `2^(TW+1)` 이어야 합니다
(TMAX 가 2의 거듭제곱이 아니면 남는 자리가 생기지만 BRAM 한 벌 안입니다).

> 합성 로그의 **`Block RAM: Final Mapping Report`** 를 보는 습관이 필요합니다.
> 기능 검증(TB 11종)은 전부 통과한 상태였고, 배선 단계에 가서야 드러났습니다.

### 붙이면서 잡은 것 — 전부 **핸드셰이크와 지연**

새 코어는 둘 다 스트리밍(valid/ready)인데 엔진 쪽은 start/done 이라 그 사이를
맞추는 자리에서만 버그가 났습니다. 산술은 한 건도 안 틀렸습니다.

| | 증상 |
|---|---|
| **첫 열 버림** | `C` 를 레지스터로 옮겨 담느라 첫 열을 흘렸더니 **그 타일이 영영 안 끝나** 출력이 한 타일씩 밀렸습니다 (다음 타일의 첫 열이 와야 앞 타일이 완성). `C` 를 그대로 씁니다 — 엔진이 step 내내 `q_NOUT` 을 잡고 있어 래치가 애초에 불필요 |
| **주소 2사이클 지연** | 읽기 주소가 레지스터라 데이터가 2사이클 뒤인데 수락 판정은 1사이클 기준 → 첫 열 중복, 타일 1부터 어긋남. 주소를 조합으로 내고 매 사이클 전진 |
| `out_c` 한 칸 앞섬 | 데이터와 같은 엣지에 증가시켜 첫 열이 1번 자리에 |
| 블로킹 대입 경쟁 | 클럭 블록에서 출력 레지스터에 블로킹 대입 → 읽는 쪽과 경쟁 |
| 재시작 루프 | `rrun` 은 마지막 주소에서 내려가는데 `done` 은 5단 뒤라 그 사이 재시작 |
| gamma/beta 정렬 | PG_Mem 이 1사이클 뒤에 답하는데 같은 사이클에 곱함 |
| 타일 카운터 미초기화 | 두 번째 LN 부터 타일 번호가 이어짐 |

## 1.6 GEMM ping-pong 누산기 — GEMM 40.7 % 단축 (**보드 264 샘플 확정**)

§1.5 로 비선형이 빠지자 프로파일(`tb_evt_prof`)이 GEMM 을 가리켰습니다:

```
PROF 총 129,696 사이클  (타임스텝 1개 + 꼬리, n_tok=52)
  GEMM 103,046 (79.5 %)   RES 17,721   LN 7,434   MEAN 903  POS 337  ARGMAX 255
```

타일 주기가 `K + 114` 인데 실제 곱셈은 `K` 뿐이었습니다 (K=128 이면 53 %).

| | 원본 | **ping-pong** |
|---|---|---|
| 타일 주기 | K + 114 | **max(K + 4, 36)** |
| GEMM / 타임스텝 | 103,046 | **61,114  (−40.7 %)** |
| 타임스텝 하나 | 129,696 | **87,717  (−32.4 %)** |

`tb_evt` 140,170 검사의 **모든 줄이 원본과 한 글자도 다르지 않습니다**

### 누산기가 하나뿐이라 막혀 있었습니다

누산기는 DSP48E2 의 `P` 하나입니다. 그래서 컬럼 32개를 **다 뽑아낼 때까지** 다음
타일을 시작할 수 없었습니다. `PE_OS_Pp` 는 PE 마다 그림자 레지스터를 둡니다:

```
P       지금 타일을 누적                 (ping)
shadow  직전 타일의 최종값을 들고 있음   (pong)   ← 읽어내기는 여기서
```

읽기와 계산이 분리되므로 배열은 곧바로 다음 타일을 받습니다.

### 전역 snapshot 이면 절반밖에 못 법니다

output-stationary 배열에서 PE 는 대각 wavefront 를 따라 끝납니다:

```
레인 i 가 k 를 내는 시각   = k + 1 + i          (Skew_Buf)
PE[i][j] 가 k 를 받는 시각 = k + 1 + i + j      (a_reg/b_reg 각 1홉)
P 에 반영                  = + 2                (DSP48E2 MREG+PREG)
⇒ PE[i][j] 확정 = K + i + j + 2
```

**PE 마다 끝나는 시각이 다릅니다.** snapshot 을 전역으로 한 번에 걸면 가장 늦은
PE[31][31](K+64)을 모두가 기다려야 해서 주기가 `K+67` 에서 멈춥니다 (−17.6 %).
`clr` 과 `snap` 을 **A 와 같은 방향으로 흘리면** PE 마다 자기 시각에 걸립니다:

```
snap_edge[i] = 펄스를 i 사이클 늦춘 것   →  PE[i][j] 에 i+j 뒤 도착
clr_edge[i]  = 마찬가지
```

주기는 이 부등식이 정합니다:

```
SNAP_PH = K + 3                       PE[i][j] 스냅 = SNAP_PH + i + j
컬럼 j 가 shadow 에 다 차는 시각      = SNAP_PH + (N-1) + j = K + 34 + j
컬럼 j 를 읽는 시각                   = K + 34 + j + RD_LEAD

① clr 는 snap 뒤                      TILE_P >= K + 4
② 다음 타일이 shadow 를 덮기 전에 읽기  TILE_P > 32
③ 컬럼 32개를 1/사이클로 소비          TILE_P >= 32
⇒ TILE_P = max(K + 4, 36)
```

### 같이 바꿔야 했던 것 둘

| | |
|---|---|
| edge mask 를 skew **앞**으로 | 예전엔 skew 뒤에서 현재 `mt`/`nt` 로 걸었습니다. 두 타일이 동시에 흐르면 배열 안 데이터는 이전 타일 것인데 `mt`/`nt` 는 이미 다음 것이라 어긋납니다. 마스크는 레인마다 상수라 주입 시점에 걸어도 같습니다 |
| 읽기가 **한 타일 뒤**에서 돎 | 컬럼을 뽑는 시점(K+35)은 이미 다음 타일의 주기 안입니다. `mt_pv`/`nt_pv` 를 쓰고, 마지막 타일을 위해 꼬리에서 주기를 한 번 더 돕니다 |

`Skew_Buf` 의 `clr` 는 **떼었습니다** — 타일이 연달아 흐르므로 flush 하면 직전 타일의
꼬리가 잘립니다. `din_valid` 가 0 인 구간은 코어가 알아서 0 을 냅니다.

## 2. attention 이 기존 MAC_OS 를 그대로 씁니다

시스톨릭 코어는 `C = A·B` 에서 **A·B 둘 다 "워드 = reduce 인덱스, 레인 = non-reduce
인덱스"** 로 읽습니다. EvT 의 GEMM 세 종류를 이 틀에 넣으면 전부 같은 식입니다:

| | 식 | reduce | B 출처 |
|---|---|---|---|
| Linear | `Σ_k A[m][k]·W[n][k]` | k | W_Mem |
| `Q·Kᵀ` | `Σ_d Q[m][d]·K[n][d]` | d = 32 | **A_Mem** |
| `attn·V` | `Σ_j attn[m][j]·V[j][n]` | j = Lk | **A_Mem** |

차이는 **B 를 어느 메모리에서 읽느냐** 하나뿐이라, `Gemm_Core_Ev` 는 `b_rd_addr` 만
내보내고 어느 메모리가 답할지는 스케줄러가 정합니다. 코어도 `PE_Array_Flat` 도
`PE_OS`(DSP48E2)도 한 벌입니다.

`attn·V` 의 A 는 softmax 출력 uint8 [0,127] 인데 이 구간은 int8 해석과 값이 같아
**unsigned 곱셈기가 필요 없습니다.**

### 새로 만든 것은 둘뿐

| | 왜 |
|---|---|
| `Transpose32` | `attn·V` 의 reduce 축이 `d`→`j` 로 바뀌는 유일한 자리라 **V 만** 축을 돌려야 함 |
| `Softmax_Attn` | 기존 `Softmax` 의 폭만 확장 (`C` 6b→8b, `CMAX` 32→128). 산술은 그대로 |

`Q`·`K` 는 `in_proj` 이 뱉는 "출력채널 하나 = 32행 컬럼" 레이아웃이 그대로 맞고,
head 4개 분할도 `a_base + h*32` 로 끝납니다 — **32 레인 타일 폭이 `head_dim` 과
같아서**입니다.

## 3. 마스킹 회로가 없습니다

EvT 는 비활성 패치를 마스킹해야 합니다. 그런데 호스트가 **활성 토큰만 보내므로**
보드에는 패딩 키가 존재하지 않습니다:

```
Lk = n_tok + 1        (+1 은 bias_k 토큰 — 원래도 절대 마스킹 안 됨)
```

`C = n_tok + 1` 하나가 마스크를 전부 표현합니다. 근거는 두 가지입니다:

1. 유효 토큰만 보내는 표현으로 264 샘플 정확도가 **정확히 재현**됨
2. 골든에서 마스크된 키의 softmax 출력이 **정확히 0** (유효 열은 125)

마스크 비트맵도 −∞ 주입도 필요 없습니다.

## 4. 주소 계획을 파이썬에서 먼저 확정합니다

`fpga_nl` 의 12 step 엔진에서도 위상·주소 버그가 5개 나왔습니다. 여기는 타임스텝당
**153 step** 입니다. 주소식을 RTL 안에서 처음 맞추면 디버깅 표면이 감당이 안 됩니다.

`sw/schedule_evt.py` 가 영역 할당과 실행 순서를 만들고 **① 영역 겹침 ② A_Mem 상한
③ 생산 전 소비** 를 검사합니다. RTL 은 그 표를 실행만 합니다.

### head-major 가 강제되는 이유

`Q·Kᵀ` 의 reduce 가 `head_dim`(32)이라 B 타일 간격이 32여야 합니다. K 를 채널순
(`K_base + kt*128 + c`)으로 저장하면 간격이 128 이라 안 맞습니다. 그래서:

```
Q[h][mt][d] = Q_base + h*(QT*32) + mt*32 + d
K[h][kt][d] = K_base + h*(KT*32) + kt*32 + d
```

그러면 head h · 행타일 mt 의 QK GEMM 이 `M=32, K=32, Nout=Lk` 로 끝나고 **코어는
손댈 게 없습니다.**

### softmax 가 GEMM 을 끊습니다

`Tile_Ctrl` 이 `for mt { for nt }` 라 행 타일이 바깥인데, QK GEMM 전체가 ~880
사이클인 반면 `Softmax_Attn` 은 행 타일 하나에 ~6,800 사이클입니다. 그래서 **행
타일마다 GEMM → softmax → AV** 로 끊습니다 (`M=32` 로 호출).

### step 프로그램이 정적입니다

`n_tok` 이 타임스텝마다 다른데(16~123), 영역 크기를 거기 맞추면 베이스가 매번 바뀌어
**프로그램을 5,182벌** 만들어야 합니다. 모든 stride 를 최악치로 고정하니 베이스가
전부 상수가 되고, 바뀌는 건 네 필드뿐입니다:

```
VAR[0] M ← n_tok    VAR[1] NOUT ← Lk    VAR[2] K ← Lk    VAR[3] C ← Lk
```

토큰 16 이든 123 이든 영역 베이스가 동일함을 실측 확인했습니다.

## 5. 골든과 하드웨어의 실행 구조 차이 (통합 TB 용)

`MAC_PROBE` 로 골든의 MAC 호출 순서를 뽑아 스케줄과 대조한 결과 **세 가지**가
확인됐습니다. 통합 TB 는 이걸 전제로 짜야 합니다.

**① in_proj 은 골든도 3개입니다.** 첫 QK 앞에 `linear_K128` 이 5개 — proc_ev 2개 +
in_proj Q/K/V 3개. `attention_forward_hw` 가 `_proj(q_in,…)/_proj(k_in,…)/_proj(v_in,…)`
로 나눠 부르기 때문입니다. **3-GEMM 분해가 맞습니다.**

**② attention 은 골든이 배치, 하드웨어가 타일링합니다.** 골든은 블록당 QK 1회 · AV
1회(head 를 텐서 축으로 batched)인데 하드웨어는 **head 4 × 행타일 3 = 12개** step
입니다. 골든 MAC 1개 ↔ 하드웨어 step 12개.

**③ `event_projection`/`preproc` 은 골든이 T 전체에 한 번, 하드웨어가 타임스텝마다**
돌립니다. `EvT.forward` 가 `(T,…)` 텐서에 먼저 적용하고 루프를 돌기 때문입니다.
같은 선형변환이라 결과는 동일하지만, **TB 는 호출 순서가 아니라 이름으로 짝지어야**
합니다.

**④ GELU 는 모듈 훅으로 6/8 을 못 잡습니다.** `EvT.py:61,65` 가
`torch.nn.GELU()(z)` 로 **매 forward 새 인스턴스**를 만듭니다 — 서브모듈이 아니라
`named_modules()` 에 안 잡힙니다. `hw_quant._patch_attention_blocks` 가
`AttentionBlock.forward` 를 통째로 갈아끼우며 `ctx['gelu1'] / ctx['gelu2']` 로
처리하므로, tap 이나 교체는 **`_hw_ctx` 를 통해야** 합니다.

    GELU 사이트 8개 = MLPBlock 2 (event_projection, preproc)
                    + AttentionBlock 3블록 x 2 (gelu1, gelu2)

`real_dvs_script/pwl_gelu.py` 가 처음에 이걸 놓쳐 **2개만 바꾼 채** 40분을 측정했고,
사이트 개수를 찍어 두지 않았으면 못 봤을 버그였습니다. 지금은 8이 아니면 중단합니다.
`taps.py` 도 같은 한계가 있으니 통합 TB 는 `ATTN_TAP`/`ctx` 를 써야 합니다.

**⑤ bias_k / bias_v 는 "키 하나"이고 자리가 매번 다릅니다.** attention 은 키가
`Lk = n_tok + 1` 개이고 마지막 하나가 학습된 상수 토큰입니다. 위치(키 인덱스
`Lk-1`)가 타임스텝마다 달라 K/V 에 써 넣으려면 읽고-고쳐-쓰기가 필요합니다. 대신
**읽는 쪽에서 끼워 넣습니다** — 호스트가 `BKV` 영역에 한 번 넣어 두고,

    QK : B 워드의 레인 = 키.  키 Lk-1 인 **레인 하나**만 바꿔치기
         (bias_k 워드는 레인 = head_dim 이라 step 시작에 한 번 읽어 둠, 주소 = AOUT)
    AV : B 워드 자체가 키 하나.  키 Lk-1 이면 **주소만** 돌림 (주소 = OSTR)

K/V 영역은 블록 3개가 돌려 쓰므로 예약 칸을 그 안에 둘 수 없습니다 — 블록마다
bias 값이 다릅니다.

**⑥ LayerNorm 입력 격자가 골든과 다릅니다 (하드웨어가 더 정밀).** 골든은
`layer_norm_1.in` 을 **Q16.-1 (lsb 2.0)** 격자에 스냅합니다 — latent 가 20
타임스텝 누적되며 커지는 범위로 잡힌 격자입니다. 하드웨어는 잔차 스트림이 bf16
이라 훨씬 촘촘합니다. 그래서 값이 작은 t=0 에서 `layer_norm_1` 의 int8 출력이
**0.4 % 자리에서 1 LSB** 갈립니다 (12,288 중 54개). 정확도에는 유리한 방향이라
설계는 그대로 두고 통합 TB 에서 **허용 오차 1** 로 둡니다.

**⑦ 골든은 ReLU 앞뒤로 두 번 양자화합니다.** `proc_ev.1` 은 ReLU 사이트 격자
(0.036535)로 한 번, 다음 GEMM 입력 격자(0.020563)로 또 한 번입니다. 뒤 격자가
**더 촘촘해서** 코드가 127 을 넘어 포화하는 자리까지 재현하려면 한 번에 접을 수
없습니다. 하드웨어도 두 번 합니다 (`FLAG2[3]`, 곱수는 레이어 뒤 빈 칸).

## 5.4 골든과 하드웨어를 **같은 비선형**으로 맞춥니다

통합 TB 가 1 LSB 차이를 전부 버그로 볼 수 있으려면, 골든의 비선형이 RTL 과 같아야

|---|---|---|

`proc_ev.1` 에 남은 불일치가 곧 §5 ⑦(2차 재양자화 누락)이라는 **진짜 버그**였습니다.

## 5.5 통합 TB 가 쓰는 검증 사슬

기대값을 **MAC 피연산자**에서 뽑습니다 (`sw/golden_steps.py`). 모듈 훅은 실수값을
주므로 step 으로 나눠 코드로 만들어야 하는데 그 매핑 표 자체가 틀리기 쉽습니다.
**어떤 GEMM 의 `a` 는 곧 그 GEMM 이 읽는 A_Mem 영역의 내용**이라 나눗셈도 반올림도
없습니다. 그리고 **어떤 step 의 출력은 다음 step 의 입력으로 검증**됩니다.

| A_Mem 영역 | 기대값 출처 | 이걸로 검증되는 step |
|---|---|---|
| `PIN` | `linear_K160.a` | event_projection + 호스트 pos enc |
| `PRE` | `proc_ev.1.a` | preproc (Q4.11→GELU→int8) |
| `EV1` | `proc_ev.4.a` | proc_ev.1 (ReLU) |
| `LNX` | `in_proj.K.a` | proc_ev.4 + RES + layer_norm_x |
| `LN1` | `in_proj.Q.a` | layer_norm_1 |

실측으로 확인된 것 (샘플 0):

* `linear_K128` 이 **타임스텝당 23개** = proc_ev 2 + 3블록 × (in_proj 3 + out_proj 1
  + linear1/2/3 3). 끝에 3개(proc_embs.linear1, clf.linear_1/2). **스케줄의 GEMM
  분해가 골든과 일치합니다.**
* `in_proj.K` 와 `in_proj.V` 의 값 범위가 **완전히 동일**(−19~109) — 둘이 같은 텐서
  (`layer_norm_x` 출력)를 읽는다는 직접 증거.
* `proc_ev.4` 의 입력이 **0 이상**(0~50) — 앞단 ReLU 가 맞는 자리에 붙었음.

## 6. 메모리와 step 워드

| | 폭 × 깊이 | 크기 |
|---|---|---|
| W_Mem | 256b × 16384 | 437 KB (14,000 워드) |
| **A_Mem** | **512b × 16384** (읽기 2포트) | 478 KB 사용 (7,645 워드) |
| PB_Mem | 256b × 1024 | 27 KB (채널 3,476) |
| PG_Mem | 256b × 256 | 6.5 KB (LayerNorm 13개) |
| Step_Mem | 256b × 256 | 3.9 KB (122 step) |

A_Mem 이 **읽기 2포트**인 이유: GEMM 만은 A 와 B 를 동시에 읽는데, `Q·Kᵀ`·`attn·V`
는 둘 다 A_Mem 입니다. 같은 내용을 BRAM 두 벌에 미러링했습니다 — BRAM 이 남고 제어가
가장 단순합니다.

### PB_Mem 은 "레이어 채널 + 뒤에 한 칸"

엔진은 step 시작(`S_GCONST`)에 `PB + NOUT` 을 한 번 읽습니다. 그 한 칸이
**레이어마다** 있어야 합니다 — 없으면 다음 레이어의 채널 0 을 읽습니다(실제로
그랬고 결과가 −128 로 포화했습니다). 그 칸에 들어가는 것은 레이어마다 다릅니다:

| 레이어 | 그 칸의 내용 |
|---|---|
| `event_projection`, `preproc`, 각 블록 `linear2` | GELU 뒤 int8 재양자화 곱수 |
| `proc_ev.1`, `clf.linear_1` | 활성함수 뒤 **2차** 재양자화 곱수 (§5 ⑦) |
| `proc_embs.linear1` | 평균(1/96) + 다음 격자 재양자화를 **한 곱수로** |
| 각 블록 `linear1` | 안 씀 — Q4.11 16비트를 그대로 저장(raw16) |
| 나머지 | 안 씀 |

LayerNorm 은 메모리를 **둘** 씁니다 — PG(gamma/beta, 특징별)와 PB(재양자화 스칼라
하나). 베이스가 다르므로 필드도 둘입니다: `PB` = 스칼라 자리, `OSTR` = PG 베이스.

### step 워드 (256b) — `EvT_Engine.v` 디코더와 한 벌

```
[ 31: 0] KIND[3:0] CONS[5:4] ACT[7:6] VAR[11:8] FLAG[15:12]
         SHIFT[21:16] GSH[27:22] FLAG2[31:28]
[ 63:32] M   [ 95:64] K   [127:96] NOUT
[159:128] AIN   [191:160] BIN   [223:192] AOUT
[255:224] PB[15:0] | OSTR[31:16]

VAR   [0] M←n_tok  [1] NOUT←Lk  [2] K←Lk  [3] C←Lk
FLAG  [0] Transpose32 경유  [1] head-major(OSTR=head stride)  [2] B는 A_Mem
      [3] raw16 — Q4.11 을 int8 로 안 내리고 16비트 그대로 저장
FLAG2 [0] LayerNorm 입력이 정수 코드 (int→bf16 변환 후 투입)
      [1] RES 두 피연산자가 정수 코드 — PB/OSTR 의 fx 상수로 스케일
      [2] B 에 bias 토큰이 붙음 (AOUT=bias_k 워드, OSTR=bias_v 워드, PB는 스칼라)
      [3] 활성함수 뒤 2차 재양자화 (곱수는 GELU 스칼라와 같은 칸, GSH)
```

필드 하나가 step 종류에 따라 다른 뜻을 갖습니다 — 워드를 늘리는 대신 **그 step 에서
확실히 노는 칸**을 씁니다. QK 는 메모리에 안 써서 `AOUT` 이 놀고, AV 는 행타일이
하나라 `OSTR` 이 놉니다.

## 7.5 보드에서 도는 순서

`Evt_Accel` 이 `fpga_nl/Nl_Accel` 과 다른 점은 **타임스텝마다 입력을 새로 받는
것**입니다. X/PIN 은 A_Mem 에 한 타임스텝분만 들어갑니다 — 20벌이면 24k 워드로
A_Mem(16k)을 넘습니다. 그래서 엔진이 `tok_req` 로 멈추고 호스트가 채워 줍니다.

```
1회      LOAD_SEL/LOAD_BASE → DMA        W(14,000) PB(869) PG(208) Step(122)
샘플마다  latinit → Z, LATV / bkv → BKV
         N_TIME=T 쓰고 CTRL.start
         T 번 {  STATUS[14] (tok_req) 대기
                 STATUS[22:17] 로 어느 타임스텝인지 읽고
                 X → A_Mem 0, PIN → A_Mem 576 을 DMA
                 TOK_N 쓰고 TOK_ACK  }
         STATUS[0] (done) 대기 → RES_CLASS
```

`fpga_nl` 은 step 12개를 AXI-Lite 레지스터 파일에 담았지만 여기는 **122 step ×
8워드 = 976 쓰기**라, Step_Mem 을 **DMA 목적지(sel 4)** 로 만들었습니다.

PIN 은 타일당 160워드를 **통째로** 보냅니다 (앞 96워드는 0). 엔진이 그 앞쪽을
`event_projection` 결과로 덮어쓰므로 내용은 상관없고, 이렇게 두면 타임스텝당
DMA 가 **X 하나 + PIN 하나**로 끝납니다. 뒤쪽 64워드만 골라 넣으면 전송이 타일
수만큼 늘어납니다.

`tb_accel_evt` 가 이 순서를 그대로 밟습니다 — 보드 SW 는 그 TB 를 옮긴 것입니다.

## 8. 엔진에서 잡은 버그

**전부 코드를 읽는 것만으로는 안 나왔습니다.** 스케줄/인코딩을 파이썬에서 확정하다
둘, 나머지는 통합 TB 를 돌리면서 하나씩 드러났습니다.

### 상수가 통째로 없던 것

| | 증상 |
|---|---|
| **`BIN`(W_Mem 베이스) 미기입** | `gemm()` 이 인자로 받은 **오프셋을 그대로** BIN 에 넣어 모든 GEMM 이 W_Mem 0번지를 읽었습니다. `event_projection` 만 우연히 맞아 앞 한 칸이 통과합니다 |
| GELU 뒤 재양자화 스칼라 | `PB + NOUT` 자리가 다음 레이어 채널 0 → −128 포화 |
| LayerNorm 뒤 재양자화 | PB(스칼라)와 PG(gamma/beta) 가 **같은 필드**를 가리키고 있었음 → `OSTR` 로 분리 |
| attention QK/AV 곱수·시프트 | `PB=0, SHIFT=0` 으로 나감. 게다가 `pb_idx = PB + col_n` 이라 **채널별로 읽고** 있었음 (attention 은 블록당 스칼라 하나) |
| `bias_k`/`bias_v`, latent 초기값 | 아예 적재 경로가 없었음 |

### 격자가 골든과 달랐던 것

| | 증상 |
|---|---|
| pos enc | export 된 표는 자기 step(0.0101) 위에 있는데 A_Mem 한 행은 **입력 step 이 하나**(0.0847). PIN 뒤쪽 64워드가 통째로 8배 |
| ReLU 앞뒤 2중 양자화 | §5 ⑦ — `proc_ev.1` 출력이 전부 어긋남 |

### 주소·제어

| | 증상 |
|---|---|
| **`w_rd_addr` 미연결** | 선언만 하고 안 이음 → W_Mem 이 뜬 주소를 읽어 가중치가 전부 X. **컴파일도 통과하고 시뮬도 안 죽습니다** |
| `q_flag[14]` | 4비트 레지스터의 범위 밖 참조 → 항상 0 |
| **`tr_r[AW_A-1:0]`** | 6비트 레지스터를 14비트로 잘라 씀 → 주소 전체가 X → V 영역이 통째로 안 써짐. 위와 같은 부류입니다 |
| LayerNorm·RES 행타일 | 둘 다 **한 바퀴만** 돌았습니다. 레인이 행이라 32행이 한 바퀴이고, `M` 이 32 를 넘으면 `base + mt*K` 로 다시 걸어야 합니다 |
| 하위 코어 `done` 이 안 내려감 | `done` 은 다음 start 까지 1 입니다. start 준 사이클에 그대로 보면 **직전 완료를 이번 완료로 착각**해 타일 하나가 통째로 건너뜁니다 → `wait_ack` |
| `Transpose32` 미구동 | 인스턴스만 있고 채우기/쏟기 코드가 없었습니다. 게다가 데이터(`cp_d`)가 조합인데 `we`/`w_idx` 를 레지스터로 둬서 **한 칸 밀린 전치**가 나왔습니다 |
| 전치 드레인이 step 을 넘김 | 마지막 23워드가 **다음 step 의 AOUT/OSTR** 로 나갔습니다 → step 종료 조건에 `!tr_run` 추가 |
| softmax 를 **두 번 start** | QK step 이 컬럼을 흘려 넣고, 뒤따르는 별도 SMAX step 이 다시 start 해 **모아 둔 입력을 지웠습니다**. softmax 를 QK step 안으로 합치고(step 153→117) 출력 주소를 `OSTR` 로 실었습니다 |
| B 데이터 조작이 **한 사이클 빨랐음** | A_Mem 은 주소를 준 **다음** 사이클에 답합니다. bias 레인 치환을 주소 조건 그대로 걸어 **한 칸 앞 워드**를 바꿨습니다. cross 블록은 우연히 안 걸리고 latent 블록에서만 터졌습니다 |
| 마지막 키 타일이 **아무도 안 쓴 자리** | latent 는 키 96개가 타일 3개를 딱 채워 bias 키(96)가 4번째 타일을 엽니다. 그 워드는 `in_proj.K` 가 쓴 적이 없어 X 로 올라오고, softmax 가 전 키를 합산하므로 **출력 전체가 X**. `Nout` 을 넘는 B 레인을 0 으로 막았습니다 |

### 보드가 잡아 준 것 — 1차 8샘플에서 6/8

시뮬이 **전부 통과한 상태로** 보드에 올렸더니 8개 중 2개가 틀렸습니다. 원인은
버그 4개였고 **뿌리는 둘**입니다.

#### 뿌리 하나 : 꼬리 5 step 이 헬퍼 밖에 있었다

본체 step 은 `gemm()` 이 manifest 에서 상수를 채우고 `annotate`/`set_ostr` 을
거치는데, 꼬리(`embs.ln`→`embs.linear1`→MEAN→`clf.linear_1`→ARGMAX)만 dict 를
직접 만들어 그 경로 밖에 있었습니다.

| | 증상 |
|---|---|
| ③ **PB/SHIFT 누락** | 인코더가 `None → 0` 으로 떨어뜨려 `embs.linear1`·`clf.linear_1` 이 **`event_projection` 채널 0 의 곱수에 시프트 0** 으로 실행. MEAN 입력 열합이 골든 280 vs **735** |
| ④ **OSTR = 0** | 쓰기 주소가 `AOUT + mt*OSTR + n` 이라 **행타일 3개가 같은 워드에 겹쳐 씀**. 뒤 64행은 직전 블록의 잔재 — ReLU 뒤인데 FFN 에 **음수 64개**(= 2타일) |

지금은 본체·꼬리를 **같은 루프**로 돌려 `annotate`/`set_ostr`/`annotate2` 를 걸고,
헬퍼를 안 거친 step 의 빠진 상수를 한 번 더 훑어 채웁니다.

#### 뿌리 둘 : `K_ARGMAX` 가 `K_GEMM` 조건문 밖에 있었다

| | 증상 |
|---|---|
| ① **채널별 상수를 안 씀** | `pb_idx` 가 `q_kind == K_GEMM` 일 때만 채널별로 움직여 10클래스가 채널 0 의 `M`·bias 공유 → 사실상 **`argmax(acc[c])`**. 채널별 M 이 1.7배까지 벌어지고(696M~1,205M) 바이어스도 −285~+175 라 접전에서 순위가 뒤집힘 |
| ② `res_class` 인덱스 한 칸 앞섬 | 파이프라인을 한 단 늘릴 때 `col_n_d` 한 줄이 남아 **클래스 10** 이 나옴 |

### 왜 시뮬이 넷 다 통과시켰나

`tb_evt` 가 **최종 클래스 하나만** 봤고, 샘플 0 은 버그 4개가 다 있어도 **우연히
9** 가 나왔습니다. 꼬리 5 step 은 값 대조가 **아예 없었습니다**.

지금은 8지점(`ZATT`·`LNA1`·`LNA2`·`FFN3`·`TFFN`·`TMEAN`·`TCLF1`·분류기 누산기)을
값으로 봅니다. 특히 **분류기 누산기 10개**를 대조하니 채널별 상수를 틀리면 못
지나갑니다. 고치는 과정에서 `TFFN` 이 12,288 중 초과 9,972 → **12** 로 줄었습니다.

> **최종 결과 하나만 보는 검증은 약합니다.** 중간값을 골든과 맞출 수 있으면
> 맞추고, 못 맞추는 자리(bf16 스트림)는 그 이유를 적어 두고 **그 다음 지점**에서
> 판정해야 합니다.

### 래퍼에서 잡은 것

| | 증상 |
|---|---|
| **`done` 을 놓침** | 엔진은 `S_DONE` 에서 `done<=1` 과 `st<=S_IDLE` 을 **같은 엣지**에 합니다. 그래서 `done` 이 뜨는 사이클엔 `busy` 가 이미 0 입니다. `busy` 로 게이팅해 래치하면 영영 못 잡습니다 — AXI 폴링도 그 한 사이클을 놓칩니다. 지금은 `busy` 와 무관하게 래치하고 `start` 에서 해제합니다 |
| `gelu_lut.vh` | `\`include` 헤더는 **프로젝트에 넣고 파일 타입을 지정**해야 합니다. `glob *.v` 로는 안 잡히고, 없으면 `create_bd_cell` 이 통째로 실패합니다 |

### TB 자체 버그 둘

* `done` 을 보고 루프를 나온 뒤 `start=0` 을 주면 엔진이 IDLE 로 가며 `done` 을
  내리는데, 그 뒤에 다시 검사해 정상 종료를 TIMEOUT 으로 오인했습니다.
* **컴파일 실패해도 직전 바이너리가 그대로 돕니다.** `run_vcs.sh` 가 `simv` 존재만
  보고 있어서, 이름 충돌로 컴파일이 깨진 뒤에도 **옛 바이너리가 돌며 같은 결과**를
  냈습니다. "고쳤는데 안 바뀐다"로 30분 헤맸습니다. 지금은 컴파일 전에 지웁니다 —
  단, **`.daidir` 까지 지워야** 합니다. 바이너리만 지우면 VCS 가 증분 판정
  (`.daidir/.vcs.timestamp`)을 보고 *"design hasn't changed"* 로 컴파일을 건너뛰어
  바이너리를 아예 안 만듭니다. 이번엔 반대로 "바이너리 없음"으로 조용히 실패합니다.
* **Verilog 는 인접 문자열을 이어붙이지 않습니다.** `$display("...aaa " "bbb", ...)`
  로 줄을 나눠 쓰면 VCS 가 그 출력을 **조용히 버립니다.** 디버그 프로브가 안 찍혀
  "안 일어난 일"로 오해하기 좋습니다.

> **사이클 4.4배를 DSP 14 %p 와 레지스터 6 %p 로 샀습니다.**

### 타이밍 여유를 어떻게 만들었나

**1차 빌드는 WNS 가 +0.001 ns** 였습니다. 닫히긴 했지만 1 ps 라, 뭐라도 하나
고치면 깨지는 상태였습니다. 크리티컬 패스가 한 덩어리였습니다:

```
1차 : PB_Mem BRAM → 4:1 서브워드 먹스 → 누산기 덧셈 → Requant_Bf16 → 레지스터
```

PB 상수를 **레지스터로 한 단** 받아 BRAM+먹스와 재양자화를 갈랐습니다. 컬럼도 한
단 늦춰 정렬을 맞췄으므로 비용은 **GEMM 타일당 1 사이클** 입니다.

```
2차 : pb_bias_q_reg → … → Requant_Bf16          WNS +0.094 ns (94배)
```

`fpga_nl` 에서 LayerNorm 을 두 군데 쪼개 −1.148 ns 를 닫았던 것과 같은 종류이고,
그때처럼 사이클 비용이 사실상 0 입니다 — PB 읽기는 GEMM 컬럼마다 한 번이라
파이프라인이 깊어져도 throughput 이 그대로입니다.

> 다만 이 파이프라인 변경이 §8 의 버그 ②(`res_class` 인덱스)를 **드러냈습니다.**
> 한 단 늘리면서 `col_n_d` → `col_n_d2` 로 바꿔야 할 곳 하나를 빠뜨렸는데, 그
> 덕에 원래 있던 버그 ①(ARGMAX 채널별 상수)까지 같이 잡혔습니다.

### 새 코어에서 다시 닫기 — **−3.083 ns 에서 시작했습니다**

코어를 갈아끼운 첫 빌드는 **5,209 엔드포인트**가 실패했습니다. 모듈별로 나누니
원인이 두 개뿐이었습니다:

| 경로 | 위반 수 | WNS |
|---|---|---|
| `u_eng → u_ln` | **3,732 (93 %)** | −3.083 |
| `u_eng → u_cp` | 253 | −0.811 |

**① LayerNorm 누산 (−3.083)** — 새 코어가 한 사이클에 다 넣어 뒀습니다:
`A_Mem BRAM → bf16→고정소수점(33b 배럴 시프트) → X²(DSP) → 47b 누산`, 논리 40단
12.78 ns. 3단으로 끊었습니다 (`P0` 변환 / `P1` 제곱 / `P2` 누산). **처리량은
그대로**고 지연만 2 clk 늘어, `recv_done` 도 같이 늦춰 S2 가 확정된 합만 읽게
했습니다.

> 이때 숨은 버그가 하나 나왔습니다 — `recv_done` 시점엔 `slot_recv` 가 **이미
> 다음 타일로 넘어가 있어서** `slot_state[slot_recv]` 가 엉뚱한 슬롯을 RECVD 로
> 표시합니다. 파이프라인이 든 `slp_p1` 을 써야 합니다.

**② Requant_Int 프리애더 (−0.811)** — 머리말에 `(acc + b_int) * M` 이 DSP48E2 의
27비트 pre-adder 에 접혀 "추가 로직 없이 공짜"라고 적혀 있었지만 **사실이
아니었습니다.** `acc` 가 32비트라 27비트 포트에 안 들어가, 패브릭 CARRY 체인이
곱셈기 앞에 그대로 붙습니다. 프리애더를 한 단 끊어 2단 → **3단**으로 만들고,
`mult`/`shift` 도 같이 등록해 레인 안으로 끌어들였습니다 (상수 하나가 DSP 64개를
먹던 팬아웃이 나뉩니다). `pb_mult_q`/`q_sh`/`g_mult_q` 에는 `(* max_fanout = 16 *)`
도 걸었습니다.

지연이 바뀌면 **연쇄로 고쳐야 할 곳이 다섯 군데**입니다:

```
CP_LAT_S 2→3,  CP_LAT_G 7→9,  CP_LAT_R 4→6      (EvT_Engine)
raw16 정렬  y_g_d2 → y_g_d3                      (Col_Post_Ev)
LayerNorm_Ev.LAT  5 → 6
tb_colpost_ev 결과 대기  4 → 12
```

**같이 넣은 가드** — `gm_done` 은 시스톨릭 배열이 다 쏟은 시점이라, 뒤에 붙은
requant/GELU 9단이 아직 값을 들고 있을 수 있습니다. 그대로 step 을 넘기면 마지막
컬럼이 **다음 step 의 AOUT/OSTR** 로 나갑니다 (전치 드레인에서 이미 겪은 실패).
`cp_busy` 로 Col_Post 파이프라인이 빌 때까지 붙잡습니다.

결과 **−3.083 → +0.006 ns**. 얇지만 slow 코너 + 클럭 불확실성(0.130 ns)까지
넣고 닫힌 정상 사인오프이고, 보드 8샘플이 8/8 로 통과했습니다. 여유가 더
필요하면 최악 경로(A_Mem BRAM → `bf16_to_fix` → DSP 입력 레지스터, 27단)의
배럴 시프트를 한 번 더 끊으면 됩니다.

> **교훈 — 지연을 줄인 코어는 조합 경로가 길어져 있습니다.** 사이클을 4.4배
> 줄인 대가가 사이클 하나당 13 ns 요구였습니다. 기능 TB 11종은 전부 통과한
> 상태였고, 이건 배선/타이밍 단계에서만 드러납니다.

| 산출물 | `build/evt_zcu102.xsa` (이미 생성됨) |

### 1. 데이터 만들기 (호스트, 한 번) — **완료됨**

`data/` 에 이미 만들어져 있습니다 (264 샘플 · 5,182 타임스텝, 워드 레이아웃
자체검증 통과). 다시 만들 일이 있을 때만 아래를 돌리면 됩니다.

```bash
EVT=/hai/home/sgh/.conda/envs/evt_new/bin/python
cd 04_basic_rtl/fpga_dvs128_10/sw
$EVT pack_evt.py          # W/PB/PG + posenc + latinit + bkv
$EVT schedule_evt.py      # 주소 계획 + stepmem.bin   ← pack 뒤에 **반드시**
$EVT export_board_evt.py  # 264 샘플 전부 (인자 없이)
```

`pack_evt.py` 를 다시 돌리면 PB 베이스가 밀리므로 `schedule_evt.py` 도 같이
돌려야 합니다. 만들어지는 용량:

| 파일 | 크기 | DDR 주소 |
|---|---|---|
| `data/wmem.bin` | 448 KB | `0x1000_0000` |
| `data/pbmem.bin` | 27.8 KB | `0x1010_0000` |
| `data/pgmem.bin` | 6.7 KB | `0x1011_0000` |
| `data/stepmem.bin` | 3.9 KB | `0x1012_0000` |
| `data/latinit.bin` | 24.6 KB | `0x1013_0000` |
| `data/bkv.bin` | 1.5 KB | `0x1014_0000` |
| `data/board/amem_x.int16.bin` | **87.1 MB** | `0x2000_0000` |
| `data/board/amem_pin.int16.bin` | **96.7 MB** | `0x3000_0000` |
| `data/board/board_index.int32.bin` | 121.5 KB | `0x4000_0000` |
| `data/board/board_samples.int32.bin` | 4.1 KB | `0x4010_0000` |

`data/board/amem_pos.int16.bin`(38.7 MB)은 **보드에 안 올립니다** — pos enc 만
따로 담은 참조용이고, 보드는 여백 96워드가 붙은 `amem_pin` 을 씁니다.

합계 184 MB — DDR low(2 GB) 안이고 서로 안 겹칩니다. 주소는 `sw/main_evt.c` 의
`DDR_*` 와 `board/load_ddr.tcl` **셋이 한 벌**입니다.

### 2. Vitis 워크스페이스

1. `source /opt/Xilinx/Vitis/2022.2/settings64.sh && vitis -workspace ws_evt &`
2. **File → New → Platform Project**
   * 이름 `evt_plat`
   * "Create from hardware specification (XSA)" → `build/evt_zcu102.xsa`
   * OS `standalone`, 프로세서 **`psu_cortexa53_0`**
   * Finish → 자동 빌드
3. **File → New → Application Project**
   * "Select a platform from repository" → 방금 만든 `evt_plat`
   * 이름 `evt_app`, 도메인 `standalone_domain`
   * 템플릿 **Empty Application (C)**
4. `evt_app/src` 에 `sw/main_evt.c` 를 복사(또는 링크)
5. **Project → Build All**

BSP 는 기본값으로 충분합니다 (`xaxidma`, `xil_cache`, `xtime_l` 은 standalone 에
기본 포함).

### 3. 주소 매크로 확인

빌드 전에 `evt_plat/.../include/xparameters.h` 에서 이름을 확인하세요:

```
XPAR_EVT_ACCEL_0_BASEADDR   0xA0010000      ← 없으면 _S_AXI_BASEADDR
XPAR_AXIDMA_0_DEVICE_ID     0
```

`main_evt.c` 는 셋 다 받아들이고 없으면 `0xA0010000` 으로 떨어집니다. BD 의
주소맵은 빌드 로그에 찍혀 있습니다:

```
/zynq_ultra_ps_e_0/Data/SEG_evt_accel_0_reg0   0x00A0010000  0x1000
/zynq_ultra_ps_e_0/Data/SEG_axi_dma_0_Reg      0x00A0000000  0x10000
```

### 4. 보드 켜고 **먼저 멈추기**

1. 보드 전원 → UART 터미널 열기 (115200)
2. **Xilinx → Program Device** 로 비트스트림 다운로드
3. `main_evt.c` 의 첫 줄에 브레이크포인트
4. **Run → Debug As → Launch Hardware (Single Application Debug)**
   → `main` 에서 멈춤

> **여기서 멈춰야 합니다.** A53 이 리셋 상태면 다음 단계의 `dow -data` 가
> `Cannot write memory if not stopped. Context Cortex-A53 #0 state: APU Reset`
> 으로 실패합니다. 디버거로 붙어야 DDR 컨트롤러도 초기화됩니다.

### 5. DDR 에 데이터 올리기 (XSCT)

Vitis 의 **Vitis → XSCT Console** 에서:

```tcl
source /경로/04_basic_rtl/fpga_dvs128_10/board/load_ddr.tcl
```

스크립트는 자기 위치 기준으로 `../data` 를 찾습니다 — 서버 절대경로를 박으면
보드 쪽 XSCT 에서 못 찾습니다. 끝에 확인이 찍힙니다:

```
검증 mrd 0x10120000 (stepmem 첫 워드):
10120000:   00000000 ...
```

184 MB 라 JTAG 로 **수 분** 걸립니다. 빨리 하려면 `--n 8` 로 샘플 수를 줄여
다시 export 하면 됩니다 (몇 초).

### 6. 실행

디버거에서 Resume. UART 출력:

**실측** (2026-08-11, ZCU102):

```
===== EvT DVS128_10 accelerator =====
VERSION = 45565401  (expect 45565401)
-- loading constants
   W 14000 / PB 869 / PG 208 / Step 122 words
-- 264 samples
    20/264  correct  20  (100.00 %)
    ...
   264/264  correct 257  (97.34 %)

===== result =====
accuracy : 257/264 = 97.34 %
golden   : 97.34 % (257/264)
time     : 28611 ms  (108377 us per sample)
last run : 10654500 cycles
```

샘플이 32개 이하면 **하나씩** 찍습니다 (`s0 T=20 label 9 pred 9 ok  … cyc`).
브링업 때 어느 샘플이 틀리는지 봐야 하므로 그렇게 해 두었습니다.

시뮬 실측이 샘플당 **10.55M 사이클 = 105.6 ms** 이고 여기에 타임스텝마다 DMA 2회
(X 최대 2.4 KB·PIN 2.6 KB)가 붙습니다.

### 7. 안 되면 여기부터

| 증상 | 원인 |
|---|---|
| `VERSION` 이 0 이나 쓰레기 | 비트스트림이 안 올라갔거나 주소가 틀림. `mrd 0xA001001C` 로 직접 확인 |
| `Cannot write memory if not stopped` | 4번을 건너뜀 — 디버거로 `main` 에 멈춘 뒤 XSCT |
| `[DMA] sel=N : M 워드 (기대 K)` | DDR 주소가 `load_ddr.tcl` 과 어긋남, 또는 파일이 안 올라감. `mrd` 로 그 주소를 직접 보세요 |
| `tok_req` 에서 멈춤 (진행 없음) | `TOK_ACK` 를 안 썼거나 `N_TIME` 이 실제 T 와 다름. `STATUS` 를 읽어 `[22:17]` 로 몇 번째 타임스텝인지 확인 |
| 정확도가 크게 낮음 | `pack_evt.py` 만 돌리고 `schedule_evt.py` 를 안 돌렸을 가능성 — PB 베이스가 밀립니다 |
| 정확도가 0 에 가까움 | LUT 초기화 실패. 합성 로그에 `>>> LUT 초기화 파일 3개 모두 읽힘` 이 있어야 합니다 |

### 8. 중간을 들여다보려면

`DUMP_BASE`/`DUMP_LEN` 을 쓰고 `CTRL[1]` 로 A_Mem 을 S2MM 으로 떠서 골든과
대조할 수 있습니다 (`tb_accel_evt` 에는 아직 안 붙였습니다). 영역 베이스는
`data/schedule.json` 에 있습니다 — 예를 들어 `LNX` 3904, `CTX` 6877.

`fpga_nl` 에서는 이 덤프가 **포맷 경계마다 끊어 보는** 수단이었습니다. 여기는
시뮬에서 이미 값 단위로 대조해 뒀으니(§1) 보드에서는 클래스만 맞으면 됩니다.

## 12. 로컬 PC 에 보드를 붙여 쓰는 법

**보드는 로컬에, 빌드는 서버에** 있습니다 (서버엔 JTAG 장치가 없습니다). 둘을
잇는 방법이 두 가지이고, **필요한 로컬 설치가 다릅니다.**

```
                 서버 (turtle)                    로컬 PC              ZCU102
   Vivado/Vitis 2022.2 · .xsa · data/      ?          USB-JTAG ──┐
                                                      USB-UART ──┴──  보드
```

### 갈래 A — 전부 로컬에서 (권장)

로컬에 **Vitis 2022.2 전체**가 있어야 합니다 (~100 GB). 대신 JTAG 가 로컬이라
DDR 적재가 빠르고, 디버깅이 편합니다.

```bash
# 서버에서 : 옮길 것만 묶기
cd 04_basic_rtl/fpga_dvs128_10/board
./make_bundle.sh          # 전체 264 샘플  → evt_board_bundle_all.tar.gz (22 MB)
./make_bundle.sh 8        # 앞 8 샘플만    → 첫 브링업용 (수 MB)

# 로컬에서
scp turtle:/hai/.../evt_board_bundle_all.tar.gz .
tar xzf evt_board_bundle_all.tar.gz
```

풀면 `build/evt_zcu102.xsa`, `sw/main_evt.c`, `board/load_ddr.tcl`, `data/` 가
나옵니다. **디렉터리 구조를 그대로 유지하세요** — `load_ddr.tcl` 이 자기 위치
기준으로 `../data` 를 찾습니다. 그 뒤는 §11 을 그대로 따르면 됩니다.

압축 22 MB 입니다 (원본 184 MB — int16 패딩이 0 이라 잘 줄어듭니다).

### 갈래 B — 서버 Vitis + 로컬 hw_server

로컬엔 **Vivado Lab Edition 2022.2**(~10 GB) 만 있으면 됩니다. `hw_server` 와
XSCT 가 들어 있습니다. 서버의 Vitis GUI 는 X11 forwarding 으로 띄웁니다.

```bash
# ① 로컬 : hw_server 띄우기 (3121 포트)
/opt/Xilinx/Vivado_Lab/2022.2/bin/hw_server        # Linux
"C:\Xilinx\Vivado_Lab\2022.2\bin\hw_server.bat"  # Windows

# ② 로컬 : 서버가 로컬 3121 에 닿게 역터널
ssh -R 3121:localhost:3121 sgh@turtle

# ③ 서버 : Vitis 를 X11 로
ssh -X sgh@turtle
source /opt/Xilinx/Vitis/2022.2/settings64.sh
vitis -workspace ws_evt &
```

Vitis 의 타깃 연결에서 `Host: localhost, Port: 3121` 을 쓰면 역터널을 타고 로컬
보드에 붙습니다. XSCT 라면 `connect -url TCP:localhost:3121`.

**UART 은 터널을 안 탑니다.** 시리얼은 로컬 USB 라 출력은 로컬 터미널에서
봅니다:

```bash
minicom -D /dev/ttyUSB1 -b 115200     # Linux (보통 UART0 이 ttyUSB1)
# Windows 는 PuTTY / Tera Term, 115200 8N1
```

### 어느 쪽이 나은가

| | A (전부 로컬) | B (서버 Vitis + 로컬 hw_server) |
|---|---|---|
| 로컬 설치 | Vitis 전체 ~100 GB | Vivado Lab ~10 GB |
| 파일 옮기기 | 22 MB 한 번 | 없음 |
| DDR 적재 184 MB | JTAG 만 | **JTAG + SSH 터널** — 훨씬 느립니다 |
| GUI | 로컬 네이티브 | X11 forwarding (반응 느림) |

**DDR 적재가 갈림길입니다.** `dow -data` 는 XSCT 가 도는 쪽(B 는 서버)에서
파일을 읽어 JTAG 로 밀어 넣습니다. 184 MB 를 터널 너머로 보내면 오래 걸립니다.
B 로 갈 거면 **`./make_bundle.sh 8` 로 8 샘플만** 먼저 올려 동작을 확인하고,
전체 정확도는 A 로 돌리거나 데이터만 로컬에 복사해 XSCT 를 로컬에서 돌리세요.

### 첫 브링업은 8 샘플로

전체 264 샘플을 바로 올리지 마세요. 8 샘플이면 X/PIN 이 수 MB 라 적재가 몇 초에
끝나고, 여기서 `VERSION` · 상수 적재 · `tok_req` 핸드셰이크 · 클래스 출력까지
전부 확인됩니다. 그게 되면 전체로 넘어가면 됩니다.

```bash
cd board && ./make_bundle.sh 8      # data/board 를 8 샘플로 다시 만들고 묶습니다
```

> `make_bundle.sh 8` 은 `data/board/` 를 **덮어씁니다.** 전체로 되돌리려면
> `cd sw && python3 export_board_evt.py` 를 인자 없이 다시 돌리세요.
